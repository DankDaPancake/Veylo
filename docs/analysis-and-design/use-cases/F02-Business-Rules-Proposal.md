# Veylo — F02 Business Rules Proposal (D-F02-1 to D-F02-8)
Performed by the BOOYAH-20 handoff team (individual attribution pending). Human review by Phạm Công Khánh is pending. Edited by Codex for the CSV alignment.



|  Name |  Content
| --- | --- |
| **D-F02-1 — Required Order Fields and Validation** | **Required:** `order_code`, `recipient_name`, `recipient_phone`, `delivery_address`, `window_start`, `window_end`, and `weight_kg`. **Optional:** `priority`, `note`, `latitude`, `longitude`. All text inputs are trimmed; required text must not be empty. **Proposed demo limits:** `order_code` is 1–40 characters comprising ASCII letters, ASCII digits, `_` or `-`; `recipient_name` is 1–100 characters; `delivery_address` is 5–255 characters. `recipient_phone` is exactly 10 digits starting with `0` (e.g. `0912345678`), with no spaces or letters after trimming; accept international formats only if the team explicitly extends the rule. `window_start` and `window_end` represent date **and** time in the hub's `Asia/Ho_Chi_Minh` timezone; `window_end` must be strictly later than `window_start` (e.g. `2026-11-20 09:00` to `2026-11-20 11:00` valid; equal or reversed invalid). `weight_kg` must be a finite numeric value greater than zero (e.g. `2.5` valid; `0`, `-1`, `abc` invalid), using kilograms throughout form/CSV/API; no unapproved upper-weight cap is introduced. If supplied, coordinates must be a pair, with latitude within `[-90, 90]` and longitude within `[-180, 180]`; `priority` defaults to `NORMAL` and allows `NORMAL` or `HIGH`. **On failure:** show field-specific messages; do not persist the invalid order. **Needs confirmation:** proposed length/phone/priority/coordinate conventions. |
| **D-F02-2 — Order Code Uniqueness** | `order_code` is **unique within each hub, case-insensitively**. Trim surrounding whitespace before comparison, and check duplicates among (1) existing database orders in the same hub and (2) rows in the same CSV file. Thus `ord-001` and `ORD-001` conflict in hub A, but the same code may exist in a different hub's test fixture. Enforce uniqueness **server-side and in the database**, not only in the UI. Duplicate records are rejected with an actionable error; no existing order is overwritten. **Example:** creating `ORD-001` after `ord-001` exists in the same hub returns `DUPLICATE_ORDER_CODE`. |
| **D-F02-3 — Atomic CSV Import and Error Reporting** | Adopt **all-or-nothing (atomic)** import: parse and validate every row, check duplicates within the upload and against the database, and create **zero** orders if any error exists. Return an error report identifying **CSV row number** (header is row 1), **column/field**, **reason**, and, when safe, the rejected value. A valid file is committed as one operation; if a uniqueness conflict occurs between validation and commit, roll back the entire import and report the conflict. Do not silently skip invalid rows, partially insert orders, or overwrite existing data. **Example:** a 100-order file with an invalid phone in row 27 yields `0 imported / 100 rejected`, with a row-27 error. |
| **D-F02-4 — CSV Format, Headers, and Limits** | Accept **`.csv` only**, encoded as **UTF-8 with or without BOM**; reject empty files, non-CSV uploads, malformed CSV and files larger than **1,000,000 bytes (1 MB)**. At most **500 data rows** plus one header row. **Proposed required header columns:** `order_code,recipient_name,recipient_phone,delivery_address,window_start,window_end,weight_kg`. **Optional header columns:** `priority,note,latitude,longitude`; if an optional column is omitted, apply the defaults from D-F02-1. Use these **exact column names** in the sample download, CSV importer, OpenSpec and tests. Parse comma-separated quoted values correctly; accept LF or CRLF line endings. **Proposed date-time format in CSV:** `YYYY-MM-DD HH:mm`, interpreted in `Asia/Ho_Chi_Minh`. Allow only the listed required and optional headers. Show an explicit error for a missing required header, any duplicate or unknown header, a malformed row or a row/file limit breach. Provide a valid template and an invalid sample with several different failure types. **Needs confirmation:** exact header spellings and date-time/size conventions. |
| **D-F02-5 — Edit, Cancel, and Concurrency** | For the **PA3 F02 slice**, a Dispatcher may **edit only an order whose current Order status is `NEW`**, and may **cancel only an order currently `NEW`**; later lifecycle cancellation policies belong to future F03/F04 decisions. Editable fields are recipient/contact, destination, delivery window, weight and optional metadata; **`order_code`, `hub_id`, audit fields and order status are not edited through the ordinary Edit form**. Cancel requires a confirmation step and a nonblank reason (proposed length 5–300 characters). Cancellation changes status to `CANCELLED`, retains the order and reason, and never hard-deletes data. Dismissing the confirmation changes nothing; cancelling an already-cancelled or non-eligible order shows an error. Detect concurrent modification with a version/last-updated check: reject stale writes, show a conflict and ask the user to refresh, rather than silently overwrite. **Examples:** `NEW → CANCELLED` allowed; `CANCELLED → edited` rejected. **Needs confirmation:** cancel eligibility and reason length. |
| **D-F02-6 — Order Status Vocabulary and Lifecycle Boundary** | Distinguish **Order** (the overall delivery request/business outcome) from **DeliveryAttempt** (an individual rider execution with its own timestamps and success/failure outcome). **Proposed PA3 F02 persisted states:** `NEW` when manual creation or CSV import succeeds, and `CANCELLED` after eligible cancellation; PA3 F02 permits `NEW → CANCELLED` and no reverse transition. This is an intentionally **limited implementation slice**, **not** a claim that these are the only statuses for the finished Veylo system. F03/F04 will need agreed assignment/delivery/final-resolution states, documented in the shared glossary and reviewed jointly with BOOYAH-14/BOOYAH-21 before their use cases are finalized. **Invariant:** a failed DeliveryAttempt must **not by itself** change the Order to a terminal failed status; Dispatcher resolution is handled through UC13. Avoid inventing a `FAILED` Order enum from an example screenshot. **Requires explicit team confirmation:** F02 status names/transitions and any shared later-state vocabulary. |
| **D-F02-7 — Authorization and Hub Scope** | A signed-in **Dispatcher** can create, import, search, view, edit and cancel **only orders belonging to the hub to which the Dispatcher is authorized**; infer `hub_id` from the trusted session/assignment, **not from a client-editable request field**. **Rider** cannot access F02 order-management actions (server returns forbidden). **Administrator** has no implied Dispatcher privileges: for the PA3 demo, deny F02 actions unless a separately approved permission explicitly grants access; the eventual administrator permission matrix is owned by BOOYAH-22/BOOYAH-13. **Proposed response policy:** unauthenticated/expired session → `401` and sign-in prompt; authenticated user lacking role → `403`; another hub's order URL → `404` to avoid disclosing the order. Enforce these checks server-side even if UI buttons are hidden. The project is scoped to one operating hub; isolated **synthetic** second-hub fixtures may be used to test authorization without declaring multi-hub operation in MVP. **Needs confirmation:** administrator policy and `403`/`404` distinction. |
| **D-F02-8 — Order Search, Filters, Sorting, Pagination** | The Orders screen (UC07) lists **only authorized hub orders**. Support case-insensitive keyword matching against **order code, recipient name or recipient phone**; filter by **Order status** and by a user-selected inclusive **date range over `window_start` in the hub timezone**. Apply filters together (AND). Default sort: **`window_start` ascending**, tie-break by `order_code` ascending for stable paging. Return **20 orders per page**, with clear next/previous navigation and total result count; reset to page 1 when filters change. The detail view shows the saved fields and current status without bypassing hub restrictions. If no results match, display an empty-result state without inventing records. **Example:** keyword `ord-`, status `NEW`, date `2026-11-20` returns only matching authorized orders, 20 per page. **Needs confirmation:** exact searchable fields and the default ascending sort. |
