## 2. Scope and Proposed Technical Direction
Performed by: Codex (planning proposal). Reviewed by: pending team review. Edited by: Codex.

Retain two actors, Hub Dispatcher and Delivery Rider, and the eight proposed functional groups: accounts/access, orders, shifts/assignments, attempts/status, rule-based recommendations, location knowledge/review, AI note normalization, and reporting.

The first application workflow should be: dispatcher creates and assigns an order; the assigned rider sees it, reads approved guidance, and records an attempt. A subsequent workflow adds a rider note, an AI-generated draft, dispatcher review, and publication. Keep order status and delivery-attempt history separate.

Proposed starting stack, subject to team experience: React + TypeScript + Vite for the responsive client, FastAPI for one modular backend, and PostgreSQL with versioned migrations. This follows the earlier research's React/FastAPI direction while applying the narrower SmartRoute MVP. Use a server-side AI adapter and a clearly labeled deterministic mock for local development. Select and pin compatible tool versions during setup.

This is an engineering recommendation, not a course requirement or a previously agreed stack. Organize by business feature; all five members must contribute across layers. A separate backend per feature is unnecessary for the proposed scope.

Defer live Shopee/SPX integration, continuous GPS tracking, traffic ingestion, learned success prediction, global fleet optimization, customer handshake, and offline synchronization. A responsive rider view is sufficient initially. Synthetic data and simulated arrival events must be labeled. An AI mock supports development but does not demonstrate the completed AI feature.

## 4. Ordered Setup Work
Performed by: Codex (task planning). Reviewed by: pending team review. Edited by: Codex.

Target: approximately 2-3 working days for the foundation, depending on member availability. T0 means the actual agreed start date. These are estimates, not dated commitments. Before work starts, create real board tasks with one named assignee, a different named reviewer, due date, and acceptance criteria. Record creation, assignment, and actual completion dates.

1. **T0: agree on working conventions.** Confirm GitHub owner, private visibility, member access, board, communication channel, stack, coding-agent integration, course calendar, and review rules. Set a simple board flow: To Do, In Progress, In Review, Done. Document that coordination roles do not replace full-stack participation.
2. **T0-T1: initialize Git and organize documentation.** Establish the proposed layout, README, ignore rules, line-ending policy, contributor instructions, issue/PR templates, and the first genuine commits. Review all existing files before adding them. Repair document links and record the PA1 gaps as open tasks. Set up the private GitHub remote and access, then use short feature branches and PRs into `main`, with one non-author review. Configure enforceable branch rules where available; record a manual equivalent if the account cannot enforce them.
3. **T1: initialize Spec Kit under `src`.** Verify the course tutorial's expected version, choose and pin a compatible official release, and record the exact installation and initialization commands. Use the selected agent integration and PowerShell-compatible scripts. Inspect generated files and retain required Markdown. Run the constitution workflow and review its output. Check that `src/.git` was not created and that a generated workflow can resolve the correct workspace.
4. **T1-T2: create a reproducible application foundation.** Scaffold the client and backend in their own directories, pin runtimes, add dependency locks, configuration validation, database startup, an initial migration, and deterministic synthetic seeds. Supply Windows-friendly setup commands, an API health endpoint, and a client screen that verifies API connectivity. Keep AI calls on the server and make local startup work without a paid AI key.
5. **T2: establish CI and verify a clean checkout.** On PRs, run client formatting/lint/type checks and build, backend checks and meaningful tests, a database migration check against a disposable database, and Markdown/link checks. Add an API/database smoke check. Have a second member follow the README from a clean checkout and report actual results before calling setup complete.
6. **T2-T3: start one scoped feature specification.** Specify the order-assignment-attempt workflow, clarify role and state rules, produce its plan/tasks, and link tasks to the board. Implement the smallest useful path if sprint capacity permits. Review the AI-normalization schema and fallback separately. Do not generate a single oversized implementation task for all eight groups.

Create board items separately for each member's Spec Kit training, PA1 survey completion, team contract, Project Plan, Vision, AI log, meetings, and submission packaging. Assign actual people during planning; no identities or completed training are assumed here.
